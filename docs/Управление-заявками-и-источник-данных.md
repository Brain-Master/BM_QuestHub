# Управление заявками и единый источник данных

**Задача:** глобальный список курсов и **удобное управление заявками** при том, что запись часто завершается на **mos.ru** в контуре школы.

## Принцип

Все тексты, цены, даты смен и списки площадок ведутся из **одного источника правды**. Сайт-агрегатор, школьные скоупы и рекламные объявления **читают** эти данные (вручную на первом этапе или через CMS/БД позже).

## Минимальная модель сущностей (для сайта и заявок)

| Сущность | Ключевые поля |
|----------|----------------|
| **Квест** | slug, название, тип (интенсив / год), возраст, навыки (список), лор (кратко), медиа (URL видео/обложки), активен в кампании да/нет |
| **Мир (сеттинг)** | slug, название, описание для хаба, стиль (дизайн-токены или ссылка на макет) |
| **Площадка** | тип (школа / база BM), название, адрес, метро, контакт школы (опционально), особенности пакета |
| **Оффер площадки** | квест + площадка + даты смены + время начала/конца дня + что входит + цена или вилка + URL mos.ru |
| **Заявка / лид** | время, источник (UTM: кампания, скоуп школы, vk), квест, площадка, контакт родителя, статус, комментарий |

## Заявки: варианты реализации по зрелости

1. **MVP:** кнопка «Записаться» ведёт на mos.ru; параллельно **событие** в аналитике (Яндекс.Метрика / GA4) с параметрами `quest_id`, `venue_id`, `scope`. Телефон/email «Вопросы» — форма на почту или в таблицу через бэкенд.  
2. **Следующий шаг:** простая **CRM** или Airtable/Notion: webhook из формы + ручной импорт лидов из VK.  
3. **Зрелость:** API школы/mos.ru или единая админка редактирования офферов (если появится).

## Школьный скоуп и аналитика

Каждая школа получает ссылку вида поддомена или `?school=slug`. Во всех событиях передавать **`school_slug`**, чтобы отличать трафик **изнутри школы** от общего списка курсов.

## Юридические границы

- Не собирать **лишние ПДн** в форме без явной цели и политики.  
- Согласовать текст **согласия** с политикой школы и BrainMaster.
