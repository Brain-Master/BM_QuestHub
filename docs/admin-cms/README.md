# BM QuestHub CMS — пакет продуктовой, UX и инженерной документации

**Версия:** 1.0.0
**Дата:** 2026-07-19
**Целевой репозиторий:** `Brain-Master/BM_QuestHub`
**Целевая система:** административная CMS для `b-master.pro`

## 1. Назначение пакета

Пакет превращает общую идею «сделать полноценную UI-систему управления контентом» в набор исполнимых контрактов:

1. продуктовая модель и границы системы;
2. подробно описанный пользовательский опыт;
3. информационная архитектура;
4. спецификации экранов, форм и состояний;
5. требования к доступности, безопасности и обратимости действий;
6. правила работы ИИ-агентов в репозитории;
7. атомарный roadmap;
8. шаблоны Task Packet и ExecPlan;
9. готовые стартовые промпты для исполнителя и оркестратора.

Документы намеренно разделены. Слабая модель не должна загружать весь пакет в контекст. Для одной задачи ей нужен `AGENTS.md`, конкретный Task Packet, соответствующая UX-спецификация и только относящиеся к задаче исходники.

## 3. Как использовать пакет ИИ-агенту

Перед любой реализацией агент обязан:

1. прочитать `02_delivery/20_AGENTS.md`;
2. получить ровно один Task Packet;
3. выполнить preflight;
4. создать или обновить ExecPlan;
5. работать только в разрешённых путях;
6. пройти перечисленные проверки;
7. остановиться после завершения текущей задачи;
8. не начинать следующий пункт roadmap без отдельного разрешения.

## 4. Порядок авторитетности

1. Явная инструкция владельца репозитория в текущем запросе.
2. `02_delivery/20_AGENTS.md`.
3. Одобренный Task Packet.
4. Одобренный ExecPlan.
5. UX и архитектурные документы этого пакета.
6. Локальная документация пакета или модуля.
7. Существующие соглашения репозитория.
8. Настройки инструментов по умолчанию.

При конфликте агент обязан остановиться и описать конфликт. Нельзя молча выбрать удобную трактовку.

## 6. Зафиксированные ограничения

- Существующий публичный сайт и snapshot-контракты должны сохранять совместимость во время миграции.
- Google Sheets нельзя отключать до проверенного импорта, периода параллельной работы и готового rollback.
- Сгенерированные JSON-снимки не являются редактируемым источником истины.
- Публикация всегда отделена от сохранения черновика.
- Любое destructive-действие должно быть обратимым либо требовать усиленного подтверждения.
- Авторизация и права проверяются сервером, а не скрытием кнопок.
- UI не должен раскрывать редактору внутренние CSS-классы, JSON-структуру или инфраструктурные секреты.

## 7. Definition of Ready для начала разработки

Разработка конкретной функции начинается только когда:

- существует Task Packet;
- известны разрешённые и запрещённые пути;
- определены acceptance criteria;
- указаны точные проверки;
- понятны затрагиваемые пользовательские сценарии;
- отсутствует неразрешённый конфликт с текущей архитектурой;
- задача не требует скрытого расширения scope.

## 8. Definition of Done для одной атомарной задачи

Задача завершена только когда:

- реализован ровно заявленный результат;
- acceptance matrix полностью PASS;
- целевые тесты прошли;
- обязательные репозиторные проверки прошли;
- ошибки и негативные сценарии покрыты;
- документация обновлена только там, где это требовалось;
- нет случайных изменений;
- выполнена независимая проверка замороженного diff;
- агент остановился и не начал следующий шаг.
