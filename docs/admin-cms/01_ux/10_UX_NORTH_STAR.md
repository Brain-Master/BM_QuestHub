# UX North Star: каким должен ощущаться продукт

## 1. Целевое ощущение

CMS должна ощущаться как спокойная, точная и обратимая рабочая система.

Не как:

- техническая консоль;
- таблица с неявными связями;
- сайт-конструктор;
- набор «магических» кнопок;
- панель, где любое действие может неожиданно попасть в production.

Целевой эмоциональный результат:

> «Я контролирую изменения. Система не даст мне незаметно сломать сайт и объяснит, что происходит».

## 2. Эмоциональная дуга типовой работы

### До начала

Пользователь часто приходит с тревогой:

- «Нужно быстро поменять расписание».
- «Главное не сломать другие площадки».
- «Я не помню, где именно это меняется».
- «Опубликовалось ли прошлое изменение?»

### Во время работы

Интерфейс должен переводить состояние в:

- ориентацию;
- уверенность;
- фокус на одной сущности;
- понимание последствий;
- ощущение сохранности работы.

### Перед публикацией

Пользователь должен понимать:

- что именно изменяется;
- какие страницы затронуты;
- есть ли ошибки;
- какая фаза займёт время;
- что можно откатить.

### После публикации

Система завершает сценарий подтверждением:

- release опубликован;
- сайт проверен;
- затронутые страницы доступны;
- есть ссылка на релиз и rollback.

## 3. Семь UX-инвариантов доверия

### UX-1. Всегда видно, где пользователь находится

На каждом экране видны раздел, сущность, статус, breadcrumb и текущий режим: просмотр, редактирование, preview или публикация.

### UX-2. Всегда видно состояние работы

Обязательные состояния:

- «Нет изменений»;
- «Есть несохранённые изменения»;
- «Сохраняем»;
- «Сохранено в 14:32»;
- «Не удалось сохранить»;
- «Обнаружен конфликт версий».

### UX-3. Сохранение не равно публикации

- `Сохранить черновик` — безопасное действие.
- `Опубликовать` — отдельное действие с summary.
- Ни одна форма не публикует автоматически.

### UX-4. Ошибка объяснима и исправима

Каждая ошибка отвечает:

1. Что не так?
2. Где проблема?
3. Что сделать?

Плохо: `Validation failed`.

Хорошо: `В формате «Полный день» время окончания 08:00 раньше времени начала 09:00. Укажите время окончания позже 09:00.`

### UX-5. Необратимые действия редки

Основной destructive action — архивирование. Физическое удаление скрыто от обычного редактора, требует отдельного permission и audit.

### UX-6. Система показывает источник значения

При наследовании:

> Адрес взят из корпуса «Школа №17, Введенского 27А».

При override:

> Для этой смены используется отдельный адрес.

### UX-7. Сложность раскрывается постепенно

Обычный редактор не видит S3 key, content hash, raw JSON, GitHub workflow и внутренние enum codes. Технические детали доступны в отдельном раскрывающемся блоке.

## 4. Принципы интерфейса

### 4.1. Calm operations

- нейтральный фон;
- один основной акцент;
- минимум декоративной анимации;
- цвет используется для смысла;
- опасные статусы не конкурируют с маркетинговой палитрой.

### 4.2. Object-first navigation

Пользователь думает «курс», «площадка», «смена», а не `catalog-snapshot`, `map` и `offers`.

### 4.3. Context before action

Перед действием показываются объект, статус, последствия и ограничения.

### 4.4. Recognition over recall

- relation picker показывает названия и контекст;
- recent items доступны;
- фильтры сохраняются;
- системные значения не нужно помнить.

### 4.5. Progressive validation

Проверки выполняются при вводе, при сохранении и при публикации всего release.

### 4.6. Visible causality

```text
Черновик сохранён
→ Проверки пройдены
→ Публикация запущена
→ Файлы собраны
→ Релиз активирован
→ Сайт проверен
```

## 5. Ментальная модель

```text
Редактировать
→ Сохранить черновик
→ Проверить
→ Посмотреть preview
→ Опубликовать
→ Убедиться
→ При необходимости откатить
```

## 6. Приоритет информации

1. что это;
2. статус;
3. основная информация;
4. действие;
5. предупреждения;
6. связи;
7. история;
8. технические детали.

## 7. UX-антипаттерны

Запрещено:

- raw JSON как основной редактор;
- одна кнопка `Save & Publish`;
- toast как единственное сообщение об ошибке формы;
- destructive action без названия объекта;
- цвет без текстового статуса;
- disabled action без причины;
- сбрасывать форму после сетевой ошибки;
- автоматически менять slug опубликованной сущности;
- показывать «успешно», если verification не завершён;
- бесконечный spinner без фазы и recovery action.

## 8. Язык интерфейса

Тон спокойный, конкретный, без обвинения пользователя и без инфраструктурного жаргона.

| Вместо | Использовать |
|---|---|
| Ошибка! | Не удалось сохранить изменения |
| Невалидные данные | Проверьте 3 поля |
| Sync started | Публикация расписания запущена |
| Delete | Архивировать |
| Are you sure? | Архивировать курс «КиберРитм»? |
| Something went wrong | Сервер не ответил. Изменения остались в форме |

## 9. Быстрота без риска

Система ускоряет повторяющиеся операции через copy, bulk edit, shortcuts, сохранённые фильтры и наследование. Она не ускоряет опасные действия ценой понимания.

## 10. UX Definition of Done

Экран не готов без:

- loading state;
- empty state;
- validation state;
- permission state;
- server error state;
- keyboard path;
- responsive behavior;
- unsaved changes protection;
- success confirmation;
- ссылок на связанные сущности;
- acceptance scenarios.
