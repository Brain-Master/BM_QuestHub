# Продуктовая концепция BM QuestHub CMS

## 1. Формулировка продукта

BM QuestHub CMS — внутренняя операционная система для управления публичным контентом BrainMaster: мирами, курсами, площадками, корпусами, сменами, форматами участия, медиа и публикациями.

Система должна позволять человеку, который не знает устройство S3, GitHub Actions, JSON и связей таблиц:

- безопасно найти нужную сущность;
- понять её текущий статус;
- изменить данные через понятную форму;
- увидеть, как изменение будет выглядеть на сайте;
- исправить ошибки до публикации;
- опубликовать согласованный набор изменений;
- подтвердить, что публикация дошла до сайта;
- при необходимости откатиться.

## 2. Проблема

Текущий процесс распределяет одну редакторскую операцию между Google Sheets, Google Drive, скриптами, GitHub Actions, S3 и статической сборкой.

Это создаёт пять системных рисков:

1. **редактор не видит результат как единое целое;**
2. **структурные ошибки обнаруживаются поздно;**
3. **связи сущностей представлены строковыми идентификаторами;**
4. **публикация воспринимается как непрозрачная техническая операция;**
5. **ответственность за корректность перекладывается с системы на память человека.**

CMS должна перенести сложность из головы редактора в модель данных, интерфейс, проверки и журнал публикаций.

## 3. Продуктовое обещание

> Редактор всегда понимает, что изменено, что сохранено, что опубликовано, что увидит посетитель сайта и как вернуться назад.

## 4. Основные продуктовые результаты

### 4.1. Управляемость

- одна каноническая сущность имеет одно место редактирования;
- связи выбираются из справочников;
- дублируемые поля заменены явными overrides;
- каждое изменение имеет автора, время и причину.

### 4.2. Предсказуемость

- черновик не влияет на сайт;
- preview использует тот же компилятор, что и публикация;
- ошибки блокируют публикацию до исправления;
- предупреждения не блокируют, но требуют осознанного подтверждения.

### 4.3. Обратимость

- каждое сохранение создаёт revision;
- каждая публикация создаёт immutable release;
- rollback меняет указатель релиза, а не пересобирает данные вручную;
- удаление контента по умолчанию является архивированием.

### 4.4. Скорость редакторской работы

- типовая смена создаётся копированием существующей;
- массовые операции поддерживают расписание;
- медиа загружаются прямо из контекста сущности;
- системные поля генерируются автоматически.

## 5. Целевые пользователи

Первичные:

- владелец продукта;
- контент-редактор;
- менеджер расписания;
- издатель, отвечающий за публикацию.

Вторичные:

- дизайнер или медиаменеджер;
- преподаватель или координатор площадки с ограниченными правами;
- технический администратор;
- аудитор с read-only доступом.

Подробные роли описаны в `../01_ux/11_PERSONAS_AND_JOBS.md`.

## 6. Продуктовые принципы

### P1. Сущности вместо файлов

Пользователь редактирует курс, смену или площадку. JSON, S3 keys и generated artifacts скрыты за системной границей.

### P2. Черновик отделён от публикации

Сохранение означает сохранение работы. Публикация означает изменение публичного состояния. Эти действия никогда не объединяются одной двусмысленной кнопкой.

### P3. Ошибка должна быть локальной

Система показывает проблему рядом с конкретным полем или объектом и объясняет исправление. Сообщение «валидация не пройдена» без указания причины считается дефектом.

### P4. По умолчанию безопасно

Нельзя случайно:

- изменить slug опубликованной сущности;
- потерять чужие изменения;
- опубликовать неполный release;
- удалить используемую площадку;
- показать секрет в браузере;
- заменить production-данные невалидным JSON.

### P5. Техническая прозрачность по требованию

Обычный редактор видит понятные статусы. Технический пользователь может раскрыть:

- revision ID;
- release ID;
- content hash;
- время компиляции;
- лог публикации;
- affected artifacts.

### P6. Один и тот же смысл везде

Термины, статусы и цвета одинаковы на списках, карточках, формах, preview и в журнале.

## 7. Non-goals первой версии

В первую версию не входят:

- универсальная headless CMS для сторонних продуктов;
- визуальный page builder;
- редактирование произвольной структуры страниц;
- полноценная CRM;
- управление оплатами;
- LMS-функции;
- автоматическая генерация маркетинговых текстов без подтверждения;
- замена публичного сайта;
- полный бренд-редизайн BrainMaster;
- микросервисная декомпозиция ради самой декомпозиции.

## 8. Метрики успеха

### 8.1. Операционные

- медианное время создания типовой смены;
- доля публикаций без rollback;
- число validation failures до и после перехода;
- количество ручных действий вне CMS;
- среднее время от сохранения до подтверждённой публикации;
- число обращений к разработчику для изменения контента.

### 8.2. Качественные

После пилота редактор должен уверенно ответить:

- «Я понимаю, опубликовано ли изменение».
- «Я знаю, где исправить ошибку».
- «Я не боюсь потерять работу».
- «Мне не нужно знать названия S3-файлов».
- «Я могу восстановить предыдущую версию».
- «Я понимаю, почему кнопка публикации недоступна».

### 8.3. Целевые показатели пилота

- не менее 90% типовых изменений выполняются без терминала и ручного редактирования таблиц;
- 100% публикаций имеют audit record;
- 100% release операций атомарны;
- 0 прямых изменений generated snapshot через UI;
- 100% конфликтов конкурентного редактирования обнаруживаются до перезаписи;
- критический сценарий «создать смену → preview → publish» проходит клавиатурой.

## 9. Ограничения и предположения

- Публичный сайт продолжает потреблять совместимые snapshot-форматы.
- Hot и cold публикации могут иметь разные SLA, но единый пользовательский язык.
- Привязки к mos.ru остаются внешней интеграцией.
- На раннем этапе допустим адаптер поверх текущего API, но он не должен закреплять редактирование raw JSON как продуктовую модель.
- PostgreSQL становится целевым источником истины после отдельного этапа импорта и cutover.
- Google Sheets сохраняются как временный источник, а затем как формат импорта/экспорта.

## 10. Продуктовая формула

```text
Спокойная работа редактора
= ясная модель сущностей
+ локальная валидация
+ видимый статус сохранения
+ preview
+ атомарная публикация
+ история
+ rollback
```
