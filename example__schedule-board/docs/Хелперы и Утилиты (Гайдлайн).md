## **1\. Executive Summary (Архитектурная философия и Бизнес-задачи)**

В идеальном, синтетическом мире бэкенд и CRM-системы отдают фронтенду безупречно отформатированные, нормализованные и готовые к мгновенному рендеру данные. В реальном же мире образовательных платформ (где массивы данных часто генерируются вручную менеджерами в AmoCRM, 1С или Битрикс24) фронтенд регулярно и неизбежно сталкивается с "грязными" строками. Это могут быть лишние неразрывные пробелы, опечатки, отсутствующие отчества, склеенные имена, нестандартные форматы дат или неожиданные null значения.

**Роль слоя утилит (Helpers & Sanitization Layer):**

В нашей React-архитектуре утилиты выполняют фундаментальную роль **Санитарного кордона (Sanitization Layer)** и **Адаптера бизнес-логики**.

Мы строго следуем паттерну "Глупые компоненты — Умные хелперы / Smart Controllers". React-компоненты (такие как CourseCard или BookingModal) вообще не должны "знать", как обрезать строку, как вычислить разницу во времени между двумя ISO-датами или как правильно распарсить ФИО. Их единственная задача — получить пропсы и максимально быстро, без лишних вычислений в основном потоке, отрендерить UI. Вся математика, тяжелая обработка строк и защита от сбоев вынесена на уровень чистых функций (Pure Functions), расположенных вне жизненного цикла компонентов.

**Стратегические преимущества такого архитектурного подхода:**

1. **Абсолютная тестируемость (Test-Driven Development):** Так как чистые функции детерминированы (для одного и того же входа всегда возвращают один и тот же выход) и не зависят от React-контекста, глобальных стейтов или хуков, их можно моментально покрыть Unit-тестами (с использованием Jest или Vitest). Это позволяет обеспечить 100% покрытие краевых случаев (Edge Cases) без необходимости монтировать тяжелые компоненты в JSDOM.  
2. **Максимальная переиспользуемость (DRY \- Don't Repeat Yourself):** Архитектура позволяет без дублирования кода использовать парсер имени наставника или алгоритм проверки архивности не только на витрине расписания, но и в Личном кабинете ученика, в корзине покупок или в виджете виджете CRM.  
3. **Defensive Design (Защитное программирование):** Интерфейс гарантированно не падает с "белым экраном смерти" (White Screen of Death) и ошибками вида Uncaught TypeError: Cannot read properties of undefined, если бэкенд неожиданно прислал некорректный тип данных или пустое поле. Каждый хелпер имеет встроенные механизмы раннего возврата (Early Return) и фоллбеков (Fallbacks).  
4. **Производительность (Performance):** Вынесение сложных регулярных выражений и преобразований дат за пределы компонентов гарантирует, что эти вычисления не будут повторно запускаться при каждом ре-рендере интерфейса (например, когда пользователь просто переключает чекбокс).

## **2\. Гуманизация данных (String Formatting & Name Parsing)**

Контент-менеджеры заносят в базу ФИО преподавателей полностью (для официальных документов, приказов и договоров). Однако в UI карточки, особенно на узких экранах мобильных телефонов, длинное трехэтажное ФИО гарантированно сломает верстку или перекроет важные элементы логистики.

### **2.1. Алгоритм formatTeacherName (Умное сокращение ФИО)**

const formatTeacherName \= (fullName) \=\> {  
  if (\!fullName) return '';  
  return fullName.split(';').map(t \=\> {  
    const parts \= t.trim().split(/\\s+/);  
    if (parts.length \>= 3\) {  
      return \`${parts\[0\]} ${parts\[1\]\[0\]}.${parts\[2\]\[0\]}.\`; // Иванов И.И.  
    }  
    return t.trim(); // Иван Иванов (оставляем как есть)  
  }).join('; ');  
};

**Инженерный разбор и защита от сбоев:**

* **Обработка массивов в строке:** Часто одну смену ведут два или три преподавателя. В реляционной базе (или из\-за ограничений выгрузки) они часто хранятся как единая строка с разделителем: "Толмачова В.В.; Юдицкий И.И.". Алгоритм сначала сплитит строку по точке с запятой, изолированно обрабатывает каждого наставника, а затем аккуратно "склеивает" массив обратно в форматированную строку.  
* **Regex очистка (Sanitization):** Специфический метод .split(/\\s+/) использует регулярное выражение для разделения слов. Если менеджер случайно поставил два, три пробела или табуляцию между Именем и Отчеством, стандартный строковый метод .split(' ') выдал бы пустые элементы в массиве и фатально сломал бы логику вывода инициалов. Регулярка \\s+ безопасно поглощает абсолютно любое количество пробелов.  
* **Умная деградация (Graceful Degradation):** Если у наставника указано только Имя и Фамилия (или это псевдоним из 2 слов), система не пытается принудительно искать отчество (что неминуемо вызвало бы ошибку парсинга parts\[2\]\[0\] is undefined), а просто и элегантно возвращает исходную строку t.trim().

### **2.2. Генератор Аватаров getInitials**

Для повышения доверия и гуманизации карточек мы используем аватары преподавателей (стильные кружочки с инициалами, наложенные друг на друга через \-space-x-2).

const getInitials \= (name) \=\> {  
  return name.replace(/\[^а-яА-Яa-zA-Z\\s\]/g, '')  
    .trim()  
    .split(/\\s+/)  
    .slice(0, 2\)  
    .map(n \=\> n\[0\])  
    .join('')  
    .toUpperCase();  
};

**Инженерный разбор:**

* **Глубокая Sanitization (Очистка от мусора):** Регулярное выражение replace(/\[^а-яА-Яa-zA-Z\\s\]/g, '') выступает в роли жесткого фильтра. Оно безжалостно вырезает все цифры, скобки и спецсимволы. Если в базе по ошибке написано "Иванов Иван (замена на смене 3)", инициалы сгенерируются кристально корректно ("ИИ"), а алгоритм не упадет на парсинге спецсимволов.  
* **Ограничение длины (Length Boundaries):** Метод .slice(0, 2\) гарантирует, что даже у людей со сложными составными или 4 именами мы возьмем исключительно первые две буквы. Три или четыре буквы физически не влезут в круглый UI-контейнер аватара и сломают центрирование.  
* **Нормализация регистра:** Вызов .toUpperCase() в самом конце цепочки приводит результат к безупречно единообразному виду, автоматически компенсируя опечатки менеджеров (например, если имя было заведено в базу с маленькой буквы).

## **3\. Математика Времени (Chronology & Time Math)**

Время — самая сложная, нестабильная и багоемкая сущность во фронтенд-разработке. Мы используем встроенный объект Date, но полностью инкапсулируем бизнес-логику в специфичные адаптеры.

### **3.1. Защита CRM checkIsAutoArchived**

const checkIsAutoArchived \= (endDateStr) \=\> {  
  if (\!endDateStr) return false;  
  return new Date() \> new Date(endDateStr);  
};

**Бизнес-логика:** Функция сравнивает дату завершения мероприятия (переданную в международном стандарте ISO 8601, например 2026-05-29T23:59:59) с локальным системным временем машины пользователя new Date().

**Импакт на бизнес:** Избавляет армию контент-менеджеров от необходимости "вручную" отслеживать и закрывать десятки завершенных смен каждый день. Полностью устраняет репутационный и финансовый риск того, что клиент сможет случайно оплатить путевку в лагерь, который закончился вчера.

### **3.2. Хронологический парсер parseStartDate (Движок сортировки)**

В наших данных (для эстетики UI) дата начала передается как красивая строка-диапазон: "15 — 19 ИЮНЯ". Стандартная сортировка массивов по алфавиту здесь потерпит полное фиаско ("15 МАЯ" лексикографически встанет после "01 ИЮНЯ"). Нам потребовалось извлечь из декоративной строки валидную математическую дату для сортировки массива.

const parseStartDate \= (timelineStr) \=\> {  
  if (\!timelineStr) return 0;  
  const parts \= timelineStr.split(' ');  
  const day \= parseInt(parts\[0\], 10);  
  const monthStr \= parts\[parts.length \- 1\].toUpperCase();  
    
  let month \= 0; // Январь (индексы месяцев в JS начинаются с 0\)  
  if (monthStr \=== 'МАЯ') month \= 4;  
  else if (monthStr \=== 'ИЮНЯ') month \= 5;  
  else if (monthStr \=== 'ИЮЛЯ') month \= 6;  
  else if (monthStr \=== 'АВГУСТА') month \= 7;  
    
  return new Date(2026, month, day).getTime(); // Возвращаем Timestamp  
};

**Инженерный разбор:**

* Алгоритм интеллектуально извлекает первый элемент строки (день старта) и последний элемент (название месяца окончания).  
* Происходит жесткий, надежный маппинг кириллических месяцев в стандартные индексы JavaScript (где 0 \= Январь, 4 \= Май).  
* **Микро-оптимизация:** Функция возвращает .getTime() — сырое число миллисекунд (Timestamp). Сравнение простых чисел работает в тысячи раз быстрее и надежнее при сортировке огромных массивов, чем ресурсоемкое сравнение полных объектов дат или строк.

## **4\. Динамическая генерация данных (Data-Driven Utilities)**

*Примечание аудита: Этот блок добавлен по результатам ревизии кода.*

Мы не хардкодим (hardcode) значения для выпадающих списков фильтров. Система автоматически адаптируется под приходящие данные.

  const realSchedule \= mockSchedule.filter(item \=\> \!item.title.includes('\[ТЕСТ\]'));  
  const schools \= \['Все площадки', ...new Set(realSchedule.map(item \=\> item.school))\].sort();  
  const programs \= \['Все программы', ...new Set(realSchedule.map(item \=\> item.title))\].sort();

Использование new Set() элегантно и сверхбыстро (с алгоритмической сложностью O(N)) извлекает только уникальные названия школ и программ из сотен карточек, отбрасывая дубликаты. Затем спред-оператор ... разворачивает их в массив, добавляя дефолтный пункт "Все площадки".

## **5\. Ядро Фильтрации и Сортировки (The Filtering Engine)**

Вся мощь и бизнес-логика интерфейса заключена в цепочке .filter().sort(), расположенной непосредственно перед рендерингом списка в компоненте App.

  const filteredSchedule \= mockSchedule.filter(item \=\> {  
    const isAutoArchived \= checkIsAutoArchived(item.endDate);  
    const isArchivedState \= item.isArchived || isAutoArchived || item.status \=== 'Отменено';  
    const displayStatus \= getDisplayStatus(item);

    // 1\. Фильтр Архива  
    if (\!showCompleted && isArchivedState) return false;  
      
    // 2\. Фильтр Площадки (С защитой тестовых данных)  
    if (selectedSchool \!== 'Все площадки' && item.school \!== selectedSchool && \!item.school.includes('\[ТЕСТ\]')) return false;  
      
    // 3\. Фильтр Программы  
    if (selectedProgram \!== 'Все программы' && item.title \!== selectedProgram && \!item.title.includes('\[ТЕСТ\]')) return false;  
      
    // 4\. Фильтр UI-Статуса  
    if (selectedStatus \!== 'Все статусы' && displayStatus \!== selectedStatus) return false;  
      
    return true; // Карточка прошла все проверки  
  }).sort((a, b) \=\> {  
    const dateA \= parseStartDate(a.timelineDate);  
    const dateB \= parseStartDate(b.timelineDate);  
      
    // Сначала сортируем хронологически (по датам)  
    if (dateA \!== dateB) return dateA \- dateB;  
      
    // Если даты совпадают, сортируем по алфавиту названия школы  
    return a.school.localeCompare(b.school);  
  });

**Архитектурные паттерны движка:**

1. **Early Return (Ранний выход):** Мы не заставляем процессор вычислять сложную логику, если карточка уже провалила первую проверку. Использование if (...) return false делает код абсолютно плоским, читаемым и избавляет от монструозных вложенных if / else конструкций (так называемого "Pyramid of Doom").  
2. **Семантическая фильтрация (Semantic Proxy):** Мы фильтруем карточки не по системному статусу из базы данных, а по вычисленному displayStatus (то, что физически видит клиент в дропдауне фильтров). То есть, если клиент выбрал "Скоро старт", движок корректно и прозрачно отобразит и статус "Согласование", и "Планируется" из БД.  
3. **Compound Sorting (Многоуровневая сортировка):** Сначала массив выстраивается строго хронологически (от мая к августу). Но если в один день (например, 1 июня) стартует сразу 10 разных смен, вступает в работу вторичная сортировка: a.school.localeCompare(b.school). Карточки с одинаковой датой аккуратно выстраиваются по алфавиту площадок, создавая идеальный, предсказуемый порядок для человеческого глаза.

*Резюме: Утилиты в нашем проекте играют роль мощного защитного слоя бизнес-логики и интерфейса. При внедрении новых форматов данных или расширении приложения, любые манипуляции со строками, датами и математическими вычислениями должны выноситься в подобные изолированные чистые функции, а не засорять тело React-компонентов.*
