# **Инженерный Гайдлайн: QA Edge Cases Matrix (Матрица тестирования и Защитное Программирование)**

**Продукт:** BrainMaster EdTech Platform (Schedule Board Module)

**Уровень документа:** Quality Assurance & Testing Strategy (Lead Level)

**Статус:** Active (Расширенная версия v2.1 — Verified & Audited)

**Целевая аудитория:** QA-инженеры (Manual & Auto), SDET-разработчики (Cypress/Playwright), Frontend-разработчики, AppSec-инженеры.

## **1\. Введение и методология тестирования EdTech-продуктов**

Данная матрица покрывает исключительно краевые, аномальные и стрессовые случаи (Edge Cases, Corner Cases). Мы исходим из того, что "Счастливый путь" (Happy Path) — сценарий, при котором бэкенд отдает идеальные данные, пользователь имеет стабильный интернет, а его действия строго линейны — уже полностью покрыт базовым набором Smoke и E2E тестов.

**Философия Defensive Programming:** В высокомаржинальном EdTech-сегменте стоимость потери лида (CAC) крайне высока. Наша система спроектирована по принципам "Защитного программирования" (Defensive Design). Это означает, что Frontend не доверяет Backend-у на 100%, а UI не доверяет пользователю.

**Цель этой матрицы:** Проверить запас прочности интерфейса и его способность к "Изящной деградации" (Graceful Degradation). Мы должны гарантировать, что:

1. При получении сломанных или неполных данных от CRM приложение не падает с "Белым экраном смерти" (White Screen of Death / Error Boundary trigger).  
2. При хаотичных или сверхбыстрых действиях пользователя система не создает дублирующиеся заявки в базе (защита от Race Conditions).  
3. При нестандартных размерах экранов или измененных системных шрифтах (Accessibility) сохраняется читабельность и возможность совершить транзакцию.

*Важно: Для проведения этих тестов QA-специалистам потребуется использовать инструменты перехвата трафика (Charles Proxy, Chrome DevTools Network Tab или Playwright Route API) для подмены ответов API на лету (Mocking).*

## **6\. Примеры автоматизированных тестов (Playwright & Cypress)**

Для ускорения процесса автоматизации тестирования (SDET) ниже приведены готовые шаблоны автотестов, покрывающие ключевые бизнес-транзакции и защиту от скачков макета (CLS).

### **6.1. Автотест на Playwright: Проверка Swap Zone (Защита от CLS)**

import { test, expect } from '@playwright/test';

test.describe('Schedule Board: Layout Stability Tests', () \=\> {  
  test('Should maintain identical card height when opening description (Swap Zone Check)', async ({ page }) \=\> {  
    // 1\. Открываем витрину расписания  
    await page.goto('/schedule');  
      
    // 2\. Выбираем первую компактную карточку в списке  
    const card \= page.locator('\[data-testid="course-card"\]').first();  
    await expect(card).toBeVisible();  
      
    // 3\. Замеряем высоту карточки ДО раскрытия описания  
    const initialBox \= await card.boundingBox();  
    const initialHeight \= initialBox?.height;  
      
    expect(initialHeight).toBeGreaterThan(0);  
      
    // 4\. Кликаем по кнопке раскрытия деталей  
    const expandButton \= card.locator('button:has-text("Подробнее о смене")');  
    await expandButton.click();  
      
    // 5\. Ожидаем завершения анимации перехода (transition duration 300ms)  
    await page.waitForTimeout(350);  
      
    // 6\. Замеряем высоту карточки ПОСЛЕ раскрытия описания  
    const expandedBox \= await card.boundingBox();  
    const expandedHeight \= expandedBox?.height;  
      
    // 7\. Сравниваем результаты: высота должна быть строго идентична (допускается погрешность в 1px из\-за округления субпикселей)  
    expect(Math.abs((initialHeight || 0\) \- (expandedHeight || 0))).toBeLessThanOrEqual(1);  
      
    // 8\. Проверяем доступность: тарифы получили класс invisible (скрыты от скринридеров)  
    const variantsContainer \= card.locator('\[data-testid="variants-container"\]');

  });

### **6.2. Автотест на Cypress: Предотвращение дублирования заявок (Race Conditions)**

describe('Schedule Board: Transactional Race Conditions', () \=\> {  
  it('Should disable booking button on first submit to prevent duplicate leads', () \=\> {  
    // 1\. Перехватываем POST-запрос создания брони и устанавливаем искусственную задержку в 1.5 секунды  
    cy.intercept('POST', '/api/v1/bookings', {  
      delay: 1500,  
      statusCode: 201,  
      body: { status: 'success', booking\_id: 'test-id' }  
    }).as('postBooking');

    // 2\. Открываем страницу и открываем модалку для первого тарифа  
    cy.visit('/schedule');  
    cy.get('button').contains('Записаться').first().click();

    // 3\. Заполняем обязательные поля валидными данными  
    cy.get('input\[placeholder="Иван Иванов"\]').type('Алексей Смирнов');  
    cy.get('input\[placeholder="+7 (999) 000-00-00"\]').type('+79998887766');  
    cy.get('input\[placeholder="Петя Иванов"\]').type('Миша Смирнов');  
    cy.get('input\[placeholder="Например: 9"\]').type('8');

    // 4\. Кликаем на отправку формы  
    cy.get('button\[type="submit"\]').click();

    // 5\. Критическая проверка: Кнопка отправки должна немедленно стать disabled  
    cy.get('button\[type="submit"\]').should('be.disabled');  
      
    // 6\. Пытаемся кликнуть повторно через cy (клик не должен произойти или вызвать ошибку)  
    cy.get('button\[type="submit"\]').click({ force: true });

    // 7\. Ожидаем завершения сетевого запроса к API  
    cy.wait('@postBooking');

    // 8\. Проверяем, что запрос ушел ровно один раз  
    cy.get('@postBooking.all').should('have.length', 1);

    // 9\. Убеждаемся, что модальное окно закрылось, а стейт обновился  
    cy.get('\[data-testid="booking-modal"\]').should('not.exist');  
    cy.get('button').contains('Принято ✅').should('exist');  
  });  
});

## **7\. Регламент заведения дефектов (Bug Reporting Protocol)**

При обнаружении несоответствия ожиданиям (Actual Result \!== Expected Behavior), задача возвращается Frontend-команде по следующему стандарту:

1. **Severity (Приоритет):** \* **P0 (Blocker):** Любые падения приложения с белым экраном (React Crash), утечки памяти, зависания бесконечного спиннера или дублирование сетевых запросов при бронировании (ST-01).  
   * **P1 (Critical):** Нарушение бизнес-логики: покупка прошедшей смены (TM-01), несоответствие статусов (API-06), перекрытие внешних ссылок (ST-03).  
   * **P2 (Major):** Дефекты верстки на брейкпоинтах (UI-01, UI-04), скачки верстки CLS (UI-05), перекрытие тегов.  
   * **P3 (Minor):** Незначительные косметические баги, опечатки.  
2. **Воспроизведение (STR):** Обязательно указывать ширину экрана (Viewport), модель мобильного устройства (если баг на таче), браузер и прикреплять подмененный JSON payload (из Charles/DevTools), на котором произошел сбой.  
3. **Визуализация:** Для дефектов из блока "Матрица UI и Верстки" (Layout Thrashing) прикрепление видео или GIF-анимации строго обязательно (чтобы разработчик видел, как именно "прыгает" интерфейс в динамике).
