## **1\. Executive Summary (Архитектурные принципы API и BFF)**

Настоящий документ фиксирует жесткий, юридически обязывающий контракт взаимодействия между клиентской частью (React SPA) и сервером (REST API).

Витрина расписания — это высоконагруженный узел системы с сильным перекосом в сторону чтения (Read-heavy node, соотношение Read/Write примерно 100:1). Главный архитектурный принцип нашего API — **"Backend for Frontend" (BFF)**. Это означает, что бэкенд не просто делает слепой SQL-дамп таблиц из реляционной базы данных, перекладывая агрегацию на клиент. Бэкенд обязан отдавать агрегированный, денормализованный, обогащенный и полностью готовый к рендерингу JSON Payload.

**Фундаментальные принципы контракта:**

1. **Strict Typing (Строгая типизация):** Недопустимо динамическое изменение типов. Если цена (price) заявлена как number, передача строки "8500" недопустима и приведет к падению фронтенд-парсера (zod/yup).  
2. **Осознанная работа с Null (Nullable vs Undefined):** Если данные физически или логически отсутствуют (например, смена не имеет интеграции с mos.ru), бэкенд обязан вернуть явный null. Тихое отсутствие ключа в JSON-ответе категорически не допускается, так как это нарушает предсказуемость деструктуризации объектов в JavaScript.  
3. **UTC & ISO 8601 (Временной консенсус):** EdTech платформа может работать в разных часовых поясах. Во избежание багов, когда "смена стартует 15 июня в Москве, но 14 июня в Калининграде", абсолютно все системные даты и метки времени передаются строго в стандарте ISO 8601 с указанием временной зоны UTC (Z). Например: 2026-06-19T23:59:59Z.  
4. **Идемпотентность мутаций:** Все POST/PUT запросы (особенно создание брони) должны обрабатываться с учетом защиты от двойных списаний или создания дублей лидов при нестабильном интернет-соединении (Double-Submit protection).

## **2\. REST Endpoints (Маршрутизация и Кэширование)**

### **2.1. Получение расписания (Read Collection)**

Эндпоинт обеспечивает загрузку всей витрины расписания. Ввиду высокой нагрузки, ответ должен кэшироваться на уровне CDN (Cloudflare/Nginx) и инвалидироваться по вебхукам из CRM.

* **Метод:** GET  
* **URI:** /api/v1/schedule  
* **Headers:** \* Accept: application/json  
* **Query параметры (Серверная фильтрация для масштабирования):**  
  * ?school\_id=uuid (Опционально. Фильтр по конкретной площадке)  
  * ?program\_id=uuid (Опционально. Фильтр по типу программы)  
  * ?status=active|planning (Опционально. Массив статусов)  
  * ?include\_archived=true|false (Опционально, по умолчанию false. Влияет на размер payload)  
  * ?limit=50\&offset=0 (Опционально. Задел для пагинации)  
* **Стратегия кэширования:**  
  * Cache-Control: public, s-maxage=300, stale-while-revalidate=600 (Кэшируем ответ на 5 минут, отдаем устаревший кэш в течение 10 минут, пока бэкенд асинхронно обновляет данные).  
* **Ответ (Success 200 OK):**  
  {  
    "data": \[ ...ScheduleItem \],  
    "meta": {  
      "total\_count": 142,  
      "filtered\_count": 45,  
      "generated\_at": "2026-05-16T12:00:00Z"  
    }  
  }

### **2.2. Создание заявки на бронирование (Create Transaction)**

*Добавлено по результатам аудита UI-компонента BookingModal.* Этот эндпоинт вызывается, когда клиент заполняет форму в модальном окне и нажимает "Забронировать".

* **Метод:** POST  
* **URI:** /api/v1/bookings  
* **Headers:** \* Content-Type: application/json  
  * X-Idempotency-Key: uuid (Генерируется на клиенте для защиты от дублей)  
* **Payload (Request Body):**  
  {  
    "variant\_id": "uuid-тарифа",  
    "parent\_name": "Иван Иванов",  
    "parent\_phone": "+7 (999) 123-45-67",  
    "child\_name": "Петя Иванов",  
    "child\_age": 9,  
    "comment": "Аллергия на цитрусовые"   
  }

* **Ответ (Success 201 Created):**  
  {  
    "status": "success",  
    "booking\_id": "new-uuid-1234",  
    "message": "Заявка успешно создана"  
  }

## **3\. TypeScript Модели (Data Schema Validation)**

Для сквозной синхронизации команд (Backend/Frontend), ниже представлены строгие TypeScript-интерфейсы ожидаемого Payload. Эти интерфейсы должны стать основой для DTO (Data Transfer Objects) на бэкенде.

### **3.1. Основная сущность: ScheduleItem**

Представляет собой единую карточку мероприятия (смену лагеря или кружок).

interface ScheduleItem {  
  /\*\* @description Строго уникальный идентификатор смены (UUID v4) \*/  
  id: string;                    
    
  // \--- Локация и Логистика \---  
  /\*\* @description Название площадки (Напр: "Школа №1517") \*/  
  school: string;                
  /\*\* @description Станция метро (Напр: "Народное Ополчение") \*/  
  metro: string;                 
  /\*\* @description Физический адрес (Напр: "ул. Живописная, 11к1") \*/  
  address: string;               
  /\*\* @description Уточнение локации. Если нет, обязательно null. \*/  
  corpus: string | null;       

  // \--- Контент и Презентация \---  
  /\*\* @description Маркетинговое название программы (без HTML) \*/  
  title: string;                 
  /\*\* @description Полное описание. Разрешен plain text. Макс длина 2000 симв. \*/  
  description: string;           
  /\*\* @description ФИО Наставников, строго разделенные точкой с запятой ";" \*/  
  teacher: string | null;        
  /\*\* @description Absolute URL к CDN (WEBP/JPEG, 16:9, min 800px). Base64 недопустим\! \*/  
  image: string;                 
  /\*\* @description Массив тегов. Не более 4 штук для UI стабильности. \*/  
  tags: string\[\];                
  /\*\* @description Строка аудитории (Напр: "6–13 лет") \*/  
  age: string;                   
  /\*\* @description Маркетинговая строка номера смены (Напр: "3 СМЕНА") \*/  
  shiftNumber: string;         

  // \--- Хронология (Критично для UI и Архивации) \---  
  /\*\* @description Визуальная строка для оси времени (Напр: "15 — 19 ИЮНЯ") \*/  
  timelineDate: string;          
  /\*\* @description Короткая строка для инфо-блока (Напр: "15 — 19 июня") \*/  
  shortDate: string;             
  /\*\* @description Точная ISO 8601 дата завершения. Используется для auto-archive. \*/  
  endDate: string;             

  // \--- Интеграции и CRM \---  
  /\*\* @description Код кружка на портале mos.ru. (Напр: "2445194") \*/  
  mosRuCode: string | null;      
  /\*\* @description Absolute HTTPS URL на страницу записи на mos.ru \*/  
  mosRuLink: string | null;      
    
  // \--- Бизнес-статус и Вместимость \---  
  /\*\* @description Сырой статус напрямую из CRM (ограничен Enum) \*/  
  status: BackendStatusEnum;     
  /\*\* @description Флаг принудительного переноса в архив менеджером \*/  
  isArchived: boolean;           
  /\*\* @description Объект, контролирующий прогресс-бар мест \*/  
  capacity: CapacityObj;         
    
  // \--- Финансы \---  
  /\*\* @description Массив тарифов. Обязателен. Если нет, передавать пустой массив \[\] \*/  
  variants: VariantObj\[\];        
}

### **3.2. Вложенные сущности (Sub-models)**

**Объект вместимости (CapacityObj):**

Используется фронтендом для рендеринга прогресс-бара и вычисления состояний "Мало мест" или "Sold Out".

interface CapacityObj {  
  /\*\* @description Общая вместимость группы. @minimum 1 \*/  
  total: number;    
  /\*\* @description Количество подтвержденных броней. @minimum 0 \*/  
  booked: number;   
}

*Жёсткое правило контракта:* Значение booked физически не может быть больше total. Если в CRM случился непредвиденный овербукинг (например, 26/24), Backend обязан нормализовать данные и отдать booked: 24, чтобы фронтенд корректно отрисовал 100% заполнения шкалы, а не 110%, ломая CSS.

**Объект тарифа (VariantObj):**

interface VariantObj {  
  /\*\* @description UUID тарифа. Отправляется обратно в POST /bookings \*/  
  id: string;            
  /\*\* @description Суть тарифа (Напр: "Интенсив (полдня)", "Абонемент") \*/  
  type: string;          
  /\*\* @description Строка расписания (Напр: "Пн-Пт, 9:00 – 12:30") \*/  
  time: string;          
  /\*\* @description Число (Integer) в рублях. Без копеек. Форматирование на клиенте\! \*/  
  price: number;         
  /\*\* @description Дополнительная информация, выводимая под тарифом \*/  
  note: string | null;   
}

### **3.3. Перечисления (Enums)**

**BackendStatusEnum:** Бэкенд не имеет права фантазировать со статусами. Возможна отдача *только* разрешенных значений из этого списка. Фронтенд использует их как ключи для маппера getDisplayStatus. Появление неизвестного статуса приведет к fallback-отображению.

enum BackendStatusEnum {  
  ACTIVE \= 'Идёт набор',  
  PLANNING \= 'Планируется',  
  APPROVAL \= 'Согласование',  
  JOIN\_LATE \= 'Можно присоединиться',  
  SOLD\_OUT \= 'Мест нет',  
  CANCELLED \= 'Отменено'  
}

## **4\. Контракт обработки ошибок и Краевые случаи (Edge Cases & HTTP Status Codes)**

Для обеспечения парадигмы **Defensive Design (Защитное программирование)**, зафиксированы строгие правила реакции системы на аномалии и сетевые сбои.

### **4.1. Ошибки бизнес-логики при бронировании (POST /bookings)**

* **HTTP 409 Conflict (Гонка бронирований):** Если клиент долго смотрел на форму, а за это время последнее место выкупили, бэкенд возвращает 409\. *Реакция UI:* Сбрасывает спиннер, показывает модальное окно с извинениями и переводит кнопку карточки в состояние "В лист ожидания".  
* **HTTP 422 Unprocessable Entity (Ошибка валидации):** Возникает, если клиент обошел frontend-валидацию (например, отправил невалидный телефон или возраст child\_age: 999). *Payload ошибки:* Бэкенд должен вернуть массив errors с указанием конкретных полей для подсветки их красным цветом в UI.

### **4.2. Несоответствие Capacity и Status (Защита от Human Error)**

**Симптом:** Менеджер руками в CRM установил статус status: "Идёт набор", но при этом математически capacity.booked \=== capacity.total. **Решение фронтенда (Зафиксировано в контракте):** Фронтенд *не доверяет* ручному текстовому статусу слепо. Внутри хелпера getDisplayStatus математика превалирует над текстом. Если места закончились, UI принудительно, игнорируя бэкенд-статус, переопределит его на Мест нет (Оранжевый) и заблокирует транзакционную кнопку (переведет в Лист ожидания).

### **4.3. Аномалии контента (Массивы и Медиа)**

* **Пустой массив тарифов (variants: \[\]):** Менеджер завел смену, но забыл прикрепить цены. *Реакция UI:* Карточка не падает (предварительная проверка variants?.length \> 0). В зоне тарифов рендерится серый плейсхолдер *"Форматы формируются"*.  
* **Битая ссылка или отсутствие изображения:** Если CDN не отвечает или поле image пустое, \<img src\> должен перехватить событие onError и подменить картинку на дефолтный брендированный fallback (заглушку).

### **4.4. Интеграция с mos.ru (mosRuLink priority)**

**Симптом:** В массиве variants есть тариф за 8500 руб, но в корневом объекте ScheduleItem передана внешняя ссылка mosRuLink: "https://...".

**Правило контракта:** Наличие внешней ссылки имеет **абсолютный приоритет** над локальным бронированием. Все кнопки "Записаться" внутри этой карточки будут перенаправлять на mos.ru (window.open), а вызов внутреннего эндпоинта POST /bookings будет невозможен. Это сделано для исключения нарушения правил воронки продаж государственного портала.

## **5\. План масштабирования API (V2 Roadmap)**

Текущий API Контракт (v1) адаптирован под быструю интеграцию с существующим MVP фронтенда, который агрессивно оперирует готовыми визуальными строками (например, timelineDate: "15 — 19 ИЮНЯ"). Для перехода к полноценной Enterprise-архитектуре (v2), в бэклог заложены следующие изменения:

1. **Передача Date Objects вместо строк:** Бэкенд перестанет склеивать строки дат. Вместо shortDate будут передаваться строгие машинные метки: startDate: "2026-06-15T09:00:00Z" и endDate: "2026-06-19T18:00:00Z". Фронтенд (используя Intl.DateTimeFormat или легковесный date-fns) возьмет локализацию, склонение по падежам и форматирование на себя, опираясь на локаль браузера клиента.  
2. **Real-Time Capacity (Server-Sent Events / WebSockets):** Текущая архитектура кэширует ответ на 5 минут. При высоких нагрузках (Black Friday распродажи путевок) вероятны коллизии. Во второй версии планируется открытие SSE-туннеля для push-уведомлений об изменении capacity.booked в реальном времени, что заставит шкалу мест на фронтенде двигаться "вживую", стимулируя мощнейшее чувство срочности (Urgency).  
3. **Cursor-based Pagination (Бесконечный скролл):** Для агрегаторов расписаний свыше 300 карточек передача единого массива станет дорогой операцией (нагрузка на сеть и RAM браузера). В v2 структура meta будет обогащена полем next\_cursor. Фронтенд внедрит паттерн Infinite Scroll (с использованием Intersection Observer API), догружая чанки (chunks) по 20 карточек по мере прокрутки.
